## 1. Применить миграцию

В SQL Editor выбранного проекта выполните **целиком** файл [`supabase/migrations/202611100001_catalog.sql`](../supabase/migrations/202611100001_catalog.sql). Он обёрнут в транзакцию: ошибка отменяет частичные изменения. Это начальная миграция, повторно после успешного применения её выполнять не нужно. Если в проекте уже есть одноимённые таблицы, сначала сопоставьте их схему; не удаляйте данные для обхода конфликта.

При использовании Supabase CLI вместо SQL Editor:

```sh
supabase login
supabase link --project-ref imhuzrhtfkhmlchfidjf
supabase db push
```

CLI и SQL Editor — альтернативные способы. Файл `supabase/config.toml` задаёт конфигурацию локальной среды. Его наличие само по себе **не изменяет настройки hosted Auth**.

Миграция создаёт:

- 8 категорий; товаров не создаёт;
- таблицы `products`, `categories`, `product_images` с RLS;
- закрытую таблицу `private.catalog_admin` для одного UUID владельца;
- проверку роли `is_catalog_admin()` и атомарное сохранение `save_catalog_product()`;
- **private** bucket `product-images`, разрешающий JPG/PNG/WebP до 8 МиБ;
- политики Storage: посетителям доступны только файлы опубликованных карточек; запись и удаление — только владельцу.

Не переключайте bucket в public: при такой настройке выдача файлов обходит SELECT-политики. [Описание контроля доступа Supabase Storage](https://supabase.com/docs/guides/storage/security/access-control).

## 2. Настроить Auth и создать владельца

В настройках Authentication вашего hosted-проекта:

1. Включите вход Email/Password.
2. Отключите регистрацию новых пользователей (`Allow new users to sign up`) и anonymous sign-ins.
3. Укажите Site URL `https://takto.uz`; разрешённый redirect при необходимости — `https://takto.uz/admin`.
4. Проверьте Auth rate limits. Ограничение попыток обеспечивает Supabase, а не JavaScript-таймер на сайте.
5. В управлении пользователями создайте один аккаунт с **вашим реальным email**. Пароль задаёт владелец самостоятельно. Подтвердите email предусмотренным провайдером способом.
6. Скопируйте UUID созданного пользователя и в SQL Editor выполните:

```sql
-- Замените UUID на реальный ID пользователя из Authentication → Users.
insert into private.catalog_admin (user_id)
values ('ЗАМЕНИТЕ_НА_UUID_ПОЛЬЗОВАТЕЛЯ'::uuid);
```

Таблица разрешает ровно одного администратора. Публичная роль, запись в `user_metadata` и обычная регистрация не дают этих прав. Не выдавайте `anon`/`authenticated` права на изменение `private.catalog_admin` и не добавляйте schema `private` в Exposed schemas.

Официальные справки: [парольная авторизация](https://supabase.com/docs/guides/auth/passwords), [ограничения запросов](https://supabase.com/docs/guides/auth/rate-limits), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

После входа пароль можно изменить в пункте «Изменить пароль» в `/admin`, без редактирования исходников. Если включена дополнительная проверка провайдера, повторно войдите перед сменой. Пароли передаются только Supabase Auth по HTTPS; приложение не сохраняет их в localStorage, URL или таблицах каталога. SDK сохраняет токены сессии для перезагрузки страницы.

## 3. Переменные и Cloudflare Pages

В существующем Pages-проекте, обслуживающем `takto.uz`, задайте для нужных окружений:

| Переменная | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | `https://imhuzrhtfkhmlchfidjf.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Publishable key из настроек API проекта; допустим legacy anon key |
| `NODE_VERSION` | `24` |

Нельзя использовать `sb_secret_…` или legacy `service_role`: Vite встраивает `VITE_*` в публичный JavaScript. Если секрет был передан в чат или другой общий канал, перевыпустите его через Supabase; он не нужен для работы этого frontend.

Параметры существующего Cloudflare Pages проекта:

- Build command: `npm run build`.
- Build output directory: `dist`.
- Root directory: корень репозитория.
- Сохранить привязку `takto.uz`, существующий Pages-проект и DNS.
- Сохранить `public/_redirects` (`/* /index.html 200`): прямое открытие `/admin`, `/catalog/...` и `/product/...` должно обслуживаться React Router.

После настройки окружения и миграции соберите Preview ветки, выполните приёмочные проверки ниже, затем разверните проверенную версию через существующую production-ветку. Отдельный сервер, Railway или Sites-хостинг не требуются. [React на Cloudflare Pages](https://developers.cloudflare.com/pages/framework-guides/deploy-a-react-site/).

Первое изменение кода/переменных требует деплоя. Дальнейшее создание и редактирование **товаров** не требует деплоев: они читаются из Supabase. Открытая страница обновляет данные раз в минуту и при возвращении фокуса; после сохранения в этой вкладке обновление запускается сразу. Новая загрузка читает актуальный каталог.

## 4. Добавить первую карточку

1. Откройте `https://takto.uz/admin`, введите email и пароль владельца.
2. Нажмите «Добавить товар»; заполните название и категорию.
3. В «Фотографии» выберите несколько JPG/PNG/WebP или перетащите файлы. Каждый файл — не более 8 МиБ/40 Мп. Браузер сохраняет пропорции, уменьшает длинную сторону до 2000 px и кодирует WebP.
4. Укажите alt-тексты, главное фото, порядок стрелками. Удалённое из формы фото окончательно удаляется после сохранения.
5. Укажите цену и единицу. Пустая цена означает «По запросу»; нулевая цена не принимается. Варианты размера, материала и отделки заполняются по одному на строку.
6. Сохраните черновик и убедитесь, что он не виден в отдельном приватном окне браузера.
7. Нажмите «Опубликовать». Проверьте карточку в каталоге и по постоянному `/product/<slug>`.
8. Перезагрузите главную. При наличии главного фото товар участвует в случайной подборке до 8 разных карточек; если товаров больше 8, попадание конкретного товара не гарантируется.

«Скрыть» переводит карточку в `archived`, сохраняя данные. «Удалить» требует подтверждения и удаляет товар и фотографии. Чтобы снова опубликовать скрытую карточку, нажмите «Опубликовать».

Старые 19 демонстрационных карточек остались в `src/data/catalog.ts`, цены — в `src/data/pricing.ts`, изображения — в `public/assets`. Они не импортируются в новую базу и не показываются новым каталогом. При необходимости переносите реальные изделия вручную через админку, начиная с черновика.

## 5. Проверки перед production

```sh
npm ci
npm test
npm run build
npm run verify:supabase
```

`verify:supabase` использует только публичный ключ, ничего не изменяет и проверяет доступность таблиц и отрицательный ответ `is_catalog_admin()` для анонимного клиента.

На Preview с настроенным Supabase проверьте:

- `/admin` без сессии, неверный пароль, верный пароль владельца, перезагрузку, смену пароля и выход;
- создание черновика, загрузку нескольких фото, обложку/порядок/alt, сохранение и публикацию;
- отсутствие черновиков у анонимного пользователя, затем появление опубликованного товара;
- редактирование, скрытие и удаление фото; отказ анонимных прямых write-запросов;
- каталог с 0, 1 и несколькими товарами, поиск/категории/избранное, карточку без цены и варианты;
- отсутствие повторов/перемешивания подборки при ререндере;
- наборы и подписку на 3/6/12 месяцев: «Состав вашей заявки» содержит выбранные условия;
- корзину с ценовыми и расчётными позициями; недоступные товары блокируют отправку;
- «Скопировать заявку», скачивание `.txt` при запрете clipboard и ссылку `@takto_order`;
- ширины 390, 768 и 1440 px, клавиатурный фокус, мобильную прокрутку наборов/карусели, отсутствие горизонтального переполнения всей страницы.

Заявка не отправляется автоматически и не принимает оплату: посетитель копирует её или скачивает и отправляет в Telegram самостоятельно. Готовые наборы используют проектные условия из `src/config/offers.ts`; окончательно подтвердите их до запуска продаж. Подписка — обсуждение условий, без автосписаний.

## 6. Файлы, ошибки и очистка

Изображения не хранятся в Git или base64 в таблицах. Публичные ссылки подписываются на 300 секунд и обновляются вместе с каталогом. Уже выданная ссылка после скрытия товара может оставаться действительной до окончания этих 5 минут; скачать файл по новой ссылке после скрытия нельзя.

Сохранение товара и метаданных всех фото проходит в одной транзакции. Конфликт редактирования в другой вкладке не затирает данные. При сетевой ошибке введённые поля остаются открытыми в форме. Отмена удаляет новые временные загрузки. Storage-политика не позволяет клиенту удалить файл, пока на него ссылается карточка: даже если ответ об успешном сохранении потерялся, отмена формы не удалит уже сохранённые фотографии.

При закрытии вкладки во время редактирования или ошибке удаления Storage могут остаться неиспользуемые файлы. Для проверки выполните read-only SQL:

```sql
select o.name, o.created_at
from storage.objects o
left join public.product_images i on i.storage_path = o.name
where o.bucket_id = 'product-images'
  and i.id is null
  and o.created_at < now() - interval '24 hours';
```

После проверки списка удаляйте только эти неиспользуемые объекты через интерфейс Storage или Storage API. Не удаляйте строки из `storage.objects` SQL-запросом: это не удаляет сами файлы. Не очищайте свежие загрузки, пока открыты формы редактирования.
